# Decisions

Rulings made while building oscalkit. The OSCAL profile-resolution specification is still a draft,
and in a few places it contradicts itself or says nothing. Each ruling below records what was
decided, why, and what it would cost if the ruling turns out to be wrong.

## Scope and inputs

- Ruling: JSON and YAML inputs only; no XML — a JSON/YAML-only design keeps the model in one typed form (the OSCAL JSON/YAML information structure is the same) and NIST publishes all content in JSON — cost if wrong: XML-only sources (and back-matter rlinks that point only at XML) cannot be resolved. These are reported as `ErrBadImport`, not silently skipped.
- Ruling: pin usnistgov/oscal-content `v1.6.0` (SP 800-53 5.2.0, OSCAL 1.2.3) and OSCAL schemas `v1.2.3` — these are the newest releases at build time, and the content was produced with that OSCAL version — cost if wrong: v1.6.0 was published days before this build. If NIST republishes a corrected release, the conformance fixtures need to be re-pinned with `scripts/fetch-nist-content.sh --update`.
- Ruling: commit the 11 MB of NIST JSON gzip-compressed (1.8 MB), with checksums of the uncompressed upstream bytes, and make every reader fall back from `x.json` to `x.json.gz` — this stays under the 20 MB repository budget while the profiles' own relative hrefs still resolve unchanged — cost if wrong: the fallback is implicit. A user with both `x.json` and `x.json.gz` present always gets `x.json`.
- Ruling: remote (`http(s)`) imports are refused unless `--allow-remote` / `FileFetcher.AllowRemote` is set — offline-by-default makes resolution reproducible, and an untrusted profile cannot trigger outbound requests — cost if wrong: profiles that import over HTTPS need an extra flag.

## Profile resolution

- Ruling: including a control does **not** include its ancestors by default; `--include-ancestors` / `Options.IncludeAncestors` enables it — the spec's prose says ancestors are included, but NIST's published PRIVACY resolved baseline (from the reference OPRXP resolver) contains `ac-3.14`, `au-3.3` and others without their parents, up-levelled into the family group. The published output is the stated acceptance target — cost if wrong: if NIST later aligns OPRXP with the prose, the default flips. It is a one-line change, and both behaviours are tested.
- Ruling: under `as-is`, groups with the same id that come from different imports are merged (controls appended in import order) — otherwise two imports of one catalog would emit two `ac` groups with a clashing id, and the spec says nothing either way — cost if wrong: a resolver that keeps both groups would produce a different, schema-dubious structure.
- Ruling: `combine: use-first` is applied *before* structuring, by removing later duplicates from each import's selection in import order. A dropped duplicate's included children are up-levelled — this matches the spec's "top-down, depth-first traversal of the import hierarchy" independently of how groups are later merged — cost if wrong: children of a discarded duplicate could appear elsewhere than another resolver would put them.
- Ruling: `combine: merge` (deprecated, "undefined behaviour") is rejected with an error, and unknown methods too. `keep` (the default) keeps clashes and emits a `duplicate-control` warning — the spec allows erroring, and guessing would produce silent differences — cost if wrong: legacy profiles that still say `merge` must be edited.
- Ruling: `as-is: false` is treated like no structuring directive, that is, `flat` — the schema allows the boolean, and "not as-is" has no other reading — cost if wrong: minimal.
- Ruling: in `custom`, selected controls are inserted without nesting (children appear only if they are selected themselves, as siblings), `order: keep` uses the flat import order, and `ascending`/`descending` use plain code-point string order — the spec says "only directly selected controls" appear, and it does not define "alphanumeric" — cost if wrong: `ac-10` sorts before `ac-2` under `ascending`; natural sort would differ.
- Ruling: a custom group whose id matches an included source group keeps its own declared title and content, and inherits the source group's params, props, links and parts after them (skipping ids already present) — this satisfies both "exact same content" and "contents MUST be copied" from the spec — cost if wrong: ordering of inherited group content may differ from other resolvers.
- Ruling: group params become loose (catalog-level) params under `flat` and `custom`, and stay in their groups under `as-is` — the spec defines any param not directly under a control as loose, but also says `as-is` keeps group content intact — cost if wrong: param placement differs; references still resolve because the ids are unchanged.
- Ruling: `set-parameters` replaces `values` and `select` with each other — the OSCAL schema allows a param to have one or the other, not both. Setting values on a selection param therefore records the chosen value and drops the choice list. Without this, the tailored Acme baseline was schema-invalid (`sc-08_odp`) — cost if wrong: the original choice list is not visible in the resolved catalog.
- Ruling: a `set-parameters` prop with a `uuid` replaces the target's prop with that uuid; other props are appended; identical links are de-duplicated — the spec says to remove existing objects "with the same distinctive ID", and props and links only have one when a uuid is present — cost if wrong: duplicate props without uuids accumulate.
- Ruling: within an `alter`, all `removes` are applied before all `adds` — this matches the XML element order (remove*, add*), and the JSON form separates the two lists — cost if wrong: an add followed by a remove matching the same content behaves differently.
- Ruling: an `add` whose `by-id` equals the control's own id is treated as implicit binding — the specification's own modify-adds example does exactly this (`by-id="a1"` on control a1) — cost if wrong: none observed.
- Ruling: for `before`/`after`, objects of the target's own kind are inserted next to it. Objects of other kinds go to the start (before) or end (after) of the container's list of that kind, because JSON cannot interleave kinds. Additions that the schema would forbid in that container (params inside a part, parts inside a param) are dropped with an `invalid-add` warning — cost if wrong: output stays schema-valid, but those additions are lost (with a warning).
- Ruling: `remove` matches `by-name` against a prop's or part's `name` and against a link's `rel`. It descends into params and parts but not into child controls. A remove with no criteria matches nothing (with a warning) — links have no `name`, and `rel` plays that role. Recursing into child controls would let one alter silently edit enhancements that have their own ids — cost if wrong: a profile expecting `by-name` to ignore links removes slightly more.
- Ruling: `oscal-version` of the output = the newest version among the profile and its imports, capped at the tool's 1.2.3; a different major version is an error — this follows the spec's metadata rule literally — cost if wrong: none.
- Ruling: metadata gets both a `source-profile` prop (required by the spec) and a `link rel="source-profile"` (what NIST's resolver emits). Both carry only the profile's file name, not its absolute path — the result conforms to the spec, stays comparable with NIST's output, and does not leak local paths — cost if wrong: consumers that need the full path must keep it themselves.
- Ruling: pruning is applied to back-matter resources (referenced as `#uuid` anywhere in surviving content, transitively) and to catalog-level loose params (referenced by inserts or `aggregates` props, or named by a set-parameter). Pruning is not applied to controls or groups beyond the as-is "no included control" rule, and `keep=always` objects always survive — this exactly reproduces NIST's back-matter in all four baselines (135/147/147/82 resources) — cost if wrong: an unreferenced loose param that another tool keeps would be missing.

## Schema validation

- Ruling: embed the four official OSCAL 1.2.3 JSON schemas and repair one defect in memory. The profile schema's `merge.combine` has `additionalProperties: false` but no `method` property, although the metaschema defines it, so every `use-first` profile fails. The fix inserts `method` (enum `use-first|merge|keep`) at compile time, and the file on disk stays byte-identical to the release — cost if wrong: if the omission were intentional, oscalkit would accept profiles that the official schema rejects.
- Ruling: for `anyOf`/`oneOf` failures, report only the branch whose failures reach deepest into the instance (ties go to the branch with the fewest failures) — OSCAL uses `anyOf` heavily (params, groups, imports), and reporting every branch buries the real error — cost if wrong: occasionally the reported branch is not the one the author intended. Validity itself is unaffected.
- Ruling: decoding is lenient (unknown fields are dropped by the typed model), and the schema is what catches unknown fields — the typed model is proven lossless on all NIST content, and the schema check is the authoritative strictness gate — cost if wrong: `resolve` on a schema-invalid profile could silently ignore an unknown directive. Validate first in CI.

## Semantic checks

- Ruling: in a *resolved* catalog (one that has a `source-profile` prop or link), `#control-id` links to controls that are not present are not reported. Unresolvable `#uuid` links are always errors — NIST's resolved baselines link to related controls outside the baseline by design (LOW alone has hundreds of such links) — cost if wrong: a genuinely broken control link in a resolved catalog goes unreported.
- Ruling: `implementation-status` values are checked against OSCAL's allowed values (`implemented|partial|planned|alternative|not-applicable`) as errors — the JSON schema does not enforce these metaschema allowed-values — cost if wrong: none.

## SSP generation and gap analysis

- Ruling: component-definition claims become by-components with status `implemented`, unless the requirement (or statement) carries an `implementation-status` prop — a component definition describes what a component *does*. The SSP author is expected to revise the status, and gap analysis surfaces everything else — cost if wrong: generated SSPs can overstate implementation until reviewed.
- Ruling: baseline controls that no component addresses get a `this-system` by-component with status `planned` and `[Placeholder]` text (disable with `--no-uncovered`) — a skeleton should contain every control to fill in, and gaps then reports these as `status-planned` warnings rather than `missing-control` errors — cost if wrong: coverage numbers count placeholders as "addressed".
- Ruling: component uuids are reused as system-component uuids, for traceability; a clash gets a fresh uuid and a warning — cost if wrong: none.
- Ruling: parameter values from component definitions are canonicalized to the catalog's current ids (resolving legacy `alt-identifier`s such as `ac-7_prm_1` → `ac-07_odp.01`). When two components set different values, the first one wins and a warning is emitted — older content uses the legacy ids, and silently keeping both would make the SSP ambiguous — cost if wrong: the "first" component (in command-line order) decides.
- Ruling: a control is *satisfied* only if its effective status (the worst across its by-components) is implemented, not-applicable or alternative, **and** it has no warning- or error-level gap. A mix of `not-applicable` and `implemented` components counts as implemented — a coverage number should mean "nothing left to do", not just "something was written" — cost if wrong: coverage looks low for SSPs that have not filled in parameters yet. `--ignore-params` relaxes this.
- Ruling: statement coverage is checked only when an implemented-requirement uses `statements`. A statement item counts as covered when it is addressed directly, through its parent statement, or through any sub-item — control-level narratives are valid OSCAL. Statement-level answers are where partial coverage becomes visible — cost if wrong: a control-level narrative that ignores items is not flagged.
- Ruling: a by-component without `implementation-status` is `unspecified`, which is a warning, and an unknown status value is also treated as `unspecified` — oscalkit cannot know what the author meant, and the semantic checker already reports invalid values as errors — cost if wrong: none.

## Engineering

- Ruling: models use value slices plus explicit deep `Clone` methods instead of JSON round-trips — resolution clones hundreds of controls, and a JSON copy of the 11 MB catalog per import would be slow — cost if wrong: a new model field must be added to `Clone`, or two outputs could share memory. `TestCloneIsDeep` guards the existing fields.
- Ruling: reference scanning for pruning marshals content to JSON once and scans for `#token` and insert directives in one pass, instead of searching for every resource uuid — about 200 resources × 10 MB of substring searches would be quadratic in practice — cost if wrong: a `#` followed by a token in plain prose counts as a reference. That can only keep extra resources, never drop needed ones.
- Ruling: YAML is converted via `yaml.Node` with an expansion budget (20 M nodes) — this keeps timestamps and `yes`/`no` tokens as text, as OSCAL requires, and defeats alias bombs — cost if wrong: YAML documents larger than about 20 M nodes are rejected.
- Ruling: the glob matcher is a hand-written linear backtracking matcher (only `*` and `?` are special), not `path.Match` — OSCAL patterns are not paths, and `path.Match` gives `[` and `\` special meanings that the spec does not mention. It is fuzzed against a regexp oracle, which found and fixed a precedence bug (`*` in the input text) — cost if wrong: patterns using character classes are matched literally.
